#C++ Socket->HTTP单文件迭代开发笔记
##核心规则：src目录仅保留socket_server.cpp, 后续开发在此基础上进行修改, GIT记录所有版本
###版本1: socket-v1: 纯Socket Server
-功能: 纯TCP字节流回显，掌握socket/bind/listen/accept/recv/send核心API

###版本2: http_min-v2: 最小HTTP Server
-增量修改: 仅改recv--send之间的逻辑，增大缓冲区为2048
-功能: 支持GET / 单路径，返回标准HTTP/1.1响应(响应行+响应头+空行+响应体)
-复用: Socket底层代码完全不变

###版本3: http-multi-3: 多路径HTTP Server
-增量扩展: 多路径判断逻辑
-功能: 支持/、/index、/about三路径访问,兼容浏览器/nc访问
-复用: Sockct底层和HTTP基础协议代码不变

###版本4：http-modular-4 多模块拆分重构
-完成项目多模块拆分重构，拆分为main入口、net网络模块、http业务处理模块、移除旧单文件socket_server.cpp
-修改CMakeLists.txt, 适配多文件编译，完成本地构建与功能验证
-在feature/http_server分支上完成代码提交，推送至远程github仓库

###版本5：v5-Fork多进程并发模式
-完成多进程HTTP服务器功能调试：修复日志宏语法错误，添加请求与静态文件日志，实现图片等二进制静态文件规范传输，优化HTTP响应格式，验证多进程PID日志输出
-适配静态文件服务基础框架，日志添加PID标识

###版本6： v6-select-concurrent-Select IO多路复用模式
-增量开发：Select并发模式，支持命令行模式切换
-核心逻辑：重构TcpServer，select()实现单进程监听多fd，最大连接数1024
-优化：修复静态文件路径/、日志拼写、增加模式标识
-验证：Select单进程处理多连接，静态文件、多并发请求响应正常
-测试：编写test_select.sh，覆盖全流程验证，新增残留进程处理

#版本7： v7-epoll-concurrent-Epoll IO多路复用模式
-增量开发：Epoll高并发模式，兼容命令行模式无缝切换（fork/select/epoll）-核心逻辑：重构TcpServer新增startWithEpoll，基于epoll_create/epoll_ctl/epoll_wait实现Linux专属高并发，ET配合accept4创建非阻塞FD，单进程高效处理多连接
-验证：完成基础功能全链条测试（单请求/静态文件/低并发）
-测试：编写test_epoll.sh实现功能自动化验证

###版本8: v8-keepalive-optimization Keep-Alive与性能优化
-增量开发：新增长连接空闲超时管理+内存池复用，基于Epoll-ET模式为完善连接与内存闭环
-核心逻辑1：TcpServer新增connections_哈希表存储fd与最后活跃时间，定时遍历检查，超过30s空闲则主动关闭连接；优化Epoll事件处理逻辑，区分空闲连接与非法空请求
-核心逻辑2：实现BufferPool缓冲区池，封装acquire/release接口，复用8KB固定大小缓冲区，减少创建销毁开销
-验证：完成超时功能端到端测试；通过ab压力测试（1000请求/10并发）验证内存池效果，RSS常驻内存稳定在3.73MB，无持续飙升

##关键收获
1.HTTP是TCP之上的应用层协议: TCP负责底层字节流传输，HTTP定义传输格式
2.真实开发: 核心文件迭代修改, 通过Git标签追溯历史版本, 避免改错无法修复
3.编译: CMake一键编译socket_server.cpp 产物隔离在build/bin
4.并发模型：新增fork的多进程是Linux下轻量并发实现方案，子进程独立运行可避免请求阻塞，通过进程PID可有效区分不同请求处理进程
5.工程规范：日志系统三服务器端开发必备，分级日志+全链路埋点可大幅提升问题排查效率；静态资源统一管理，二进制读取+正确MIME类型是图片等非文本资源正常传输关键
6.Select是跨平台基础IO多路复用方案：单进程通过轮询监听多个fd状态实现并发，无需创建子进程，资源占用低
7.Select-IO多路复用问题解决：fork多进程资源开销大，调度/创建销毁成本高，无必要的进程间资源竞争问题
8.Epoll是Linux专属高并发方案：内核事件回调实现O(1)事件通知，ET模式配合非阻塞IO，避免了单连接IO阻塞导致整个服务卡断；通过accept4直接创建非阻塞客户fd，简化高并发下fd管理
9.Epoll问题解决：突破Select 1024连接的限制，由内核通知就绪fd，无需再遍历所有fd，将O(n),提升至O(1)
10.长链接优化核心：Keep-Alive提升连接复用率，但需配套超时机制避免空闲连接资源泄漏，通过fd活跃时间计时可精准管控连接生命周期
11.内存池价值：高频IO场景下缓冲区复用可大幅度降低内存分配/释放开销，避免内存碎片，RSS常驻内存稳定是复用生效的核心判断指标
12.EPOLL ET模式细节：区分”请求不完整关闭“与”空闲超时关闭“逻辑，纯空闲连接需跳过请求合法性校检，进入超时计时流程
13.多进程与数据库连接冲突：fork多进程模型下，主进程与子进程共享数据库连接会导致查询中断、连接丢失，是服务器不稳定的核心原因
14.单例模式工程应用：数据库单例可简化全局调用，但在多进程场景下并非线程/进程安全，需要配合重连机制保障可用性
15.用户系统安全基础：密码必须采用加盐哈希存储，禁止明文保存；登录通过密文对比实现，符合基础安全规范
16.HTTP API开发要点：POST接口需要正确解析请求体，参数名称拼写、路由匹配直接影响端口可用性
17.线程池并非通用优化方案：快速内存级HTTP响应下，线程池会因线程切换、任务队列开销导致性能下降，仅对数据库/文件IO等慢任务有正向收益
18.Reactor模型标准分工：Epoll主线程只做IO事件分发，耗时业务下沉至线程池，可避免单线程阻塞拖垮整个服务
19.并发模型要匹配业务特征：IO密集型且无阻塞逻辑->单线程Epoll最优；存在阻塞型操作->线程池异步化才有意义
20.多线程下线程安全：异步任务执行时需保证fd有效，避免连接已关闭后仍读写导致异常
21.压测是架构验证的核心手段：通过wrk量化指标可直接判断架构合理性，避免凭经验盲目选用多线程
22.LRU缓存适合读多写少的场景，可显著提升用户认证性能；缓存一致性需注意，但用户数据稳定性高，适用性强
23.单元测试是服务稳定性保障：核心网络与HTTP接口必须通过用例覆盖边界场景，避免重构后逻辑退化
